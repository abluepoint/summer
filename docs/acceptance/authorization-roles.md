## 变更与实际行为

原后端允许两个 JVM 使用同一个版本更新角色，双方都返回 200/version 2，后一写覆盖前一写。角色和用户绑定现在在数据库事务内按资源、企业和 expectedVersion 条件更新；未命中返回 `412 SUMMER_PRECONDITION_FAILED`。只有胜者写入变更审计及 outbox，节点投影和幂等回执在提交后发布。授权决策审计仍作为独立事实保留，不与业务变更审计混淆。

新候选的真实 MySQL、PKCE 和双 JVM 复验中，角色竞争和绑定竞争均为一个 200、一个 412。两个节点回读版本和内容一致。角色更新在领取版本后因无效名称返回 400，版本保持 2，无失败变更的审计/outbox；同一幂等键随后可正常提交版本 3。节点重启后，角色、绑定和变更审计仍可读取。

原角色页面始终提交 `If-Match: "1"`，第三次保存无法撤销拒绝。页面现在读取当前绑定，保留保存返回的新版本；412 后更新版本并保留用户输入，由用户核对后重试。真实 Chrome 三次保存提交 `"1"`、`"1"`、`"2"`，返回版本 1、2、3；业务 API 依次为 200、403、200。
