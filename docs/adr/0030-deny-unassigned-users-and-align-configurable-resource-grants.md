# 默认拒绝未分配主体，并统一可配置资源的权限码

## 背景

Summer4 的接口扫描、角色配置、菜单可见性与本地登录必须使用同一授权模型。OAuth 请求 scope 不能替代角色授权；前端读取权限失败也不能生成管理员权限。技术方案见 [#108](https://github.com/abluepoint/summer/issues/108)，接口配置与角色、数据权限见 #123、#124。本文补充 ADR 0026、0027、0029，不改变 public client + PKCE 的四项 OAuth scope 契约。

## 决策

- 未持久分配角色的主体默认拒绝业务接口。托管主体的绑定被删除后也不得退回 scope 授权。已有绑定还必须满足有效企业成员关系，角色和能力不得跨租户借用。
- Sample 的无企业路径业务接口属于 `ent-acme`；不能使用 JWT 中第一个企业作为业务数据所属企业。带企业路径的接口按路径企业校验成员关系。
- 本地未托管管理员只保留初始化角色、能力、接口目录和菜单所需的明确权限，不自动获得业务数据访问。首次选择内置能力创建角色时，在相同写事务中持久化这些能力；企业能力归属当前企业，平台能力保留 PLATFORM 范围。建立托管绑定后，以持久角色为准。
- `summer.sample.authorization.legacy-scope-compatibility` 默认关闭。显式开启时仅允许非本地、非托管的旧主体沿用原方法 scope 门禁；本地用户及托管主体不参与兼容。测试配置显式启用该开关以保留旧合成 JWT fixture，严格默认值另有独立回归。部署不得把测试开关当成默认配置。
- 未声明权限码的接口使用扫描得到的 HTTP method + 规范化路由模板，判定时也使用 Spring 实际匹配模板。权限管理接口显式声明语义权限码，以保持扫描目录、角色配置、重新登录后的 claims 与服务方法门禁一致。BUSINESS 接口可配置，协议和基础设施接口保持其分类保护。
- 加入企业前的申请、补充、撤回及受邀令牌消费，只在真实 InvitationController 的精确方法与路径上沿用其主体、令牌、状态校验。读取与退出自己的会话无需角色授权；会话列表和他人会话操作仍走授权。可见菜单只在真实菜单控制器中沿用成员与逐项权限校验。
- 前端独立尝试发布 manifest 与读取可见菜单；发布失败不得阻止普通用户读取自己的菜单。空结果和读取失败保持空权限。初始化管理菜单使用后端语义权限码，元数据变化提升 manifest 版本。
- 权限变更与菜单变更的审计先写入持久表，再写 outbox，同事务提交或回滚。ALLOW/DENY 决策使用独立事务保留，包含请求关联、主体、权限码与原因；不保存 Token、任意正文或完整授权列表。V31 追加审计资源、动作与主体列，不修改已发布迁移。

## 验证与边界

真实 PKCE 回归覆盖管理员初始化、角色分配、重新登录与再次管理，同时验证业务接口仍拒绝；纯单测覆盖默认拒绝、显式兼容、成员与多角色数据范围；HTTP 回归覆盖模板权限、显式 DENY、申请人主体限制和自身会话。审计回归验证重建服务后读取，以及变更、审计、outbox 的回滚一致性。

这些决策不等于 T01–T36 的生产验收全部完成。真实 BFF/独立连接服务、浏览器全流程、集群故障演练、负载与发布环境验收，应按各自技术方案单独提供证据。
