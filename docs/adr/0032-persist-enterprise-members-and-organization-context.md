# Persist enterprise membership and validate organization context

Status: accepted for the Summer Sample directory. Extends ADR 0030's default-deny boundary; it does not replace the authorization decision service.

## Decision

Enterprise members have durable tenant/member and tenant/subject identities. An email is contact information, not a derived authentication subject. Member status, organization assignments, current-context selection and local identity refresh use this directory. The configured local bootstrap username receives an explicit sample membership; startup never reactivates an existing disabled membership. V36 performs a one-time compatibility conversion of existing active local users with persisted tenant role bindings. Future role bindings alone do not establish membership.

Organization reads load persisted units and assignments. Parent ownership, active member status, organization state, cycles and subtree depth are checked within the selected tenant. Organization IDs are independent of codes, allowing separate tenants to use the same code. PATCH distinguishes an absent parentId from an explicit null that moves a unit to the root. Conditional writes retain If-Match and Idempotency-Key; a tenant enterprise-row lock protects the version check and durable mutation receipt. Member-status/organization mutation audit and receipts commit in the same database transaction. Organization entity versions prevent an update from silently replacing the database row.

GET and PUT `/api/v1/enterprises/{enterpriseId}/context` return the authenticated subject's selected organization. The existing single active context per subject is retained. Selection requires an active persisted member, an active organization in that tenant and a current assignment. GET returns a null organization when the saved selection no longer qualifies. Identity refresh removes stale organization and tenant claims, and emits a tenant-qualified organization_context only for a valid selection.

Organization handlers declare `enterprise.organization.read/write`; member handlers declare `enterprise.members.read/write`. Persisted role grants are still required; method scopes do not override default denial. AuthorizationService also checks current ACTIVE membership and ACTIVE enterprise for each decision, so a disabled/deleted member cannot keep using an old valid JWT. The configured bootstrap account is checked against the same durable membership; role bindings never recreate a removed member. Legacy singular/plural organization scopes remain method-security aliases, while persisted grants use the singular stable permission code.

Accepted invitations bind the actual authenticated subject to a persisted member. An opaque subject must present the matching verified email; an issuer whose subject itself is the invited address remains compatible. Join applications retain the submitting subject so another subject with the same address cannot edit them. Accepted organization assignments use the same persisted directory. This bridge does not convert arbitrary invitation capability text into authorization grants.

The platform enterprise directory, enterprise review and enterprise creation share `summer_enterprise`. Freeze/disable/reject writes durable enterprise state, preventing fresh local membership claims for inactive enterprises. Review decisions and action receipts/audit are durable. Showcase companies, credentials and counts are no longer substituted for repository data; unavailable DID, license, qualification, resources and activity remain empty. Enterprise review materials remain empty until a real materials subsystem supplies them.

## Boundaries and migration

V35 adds the member directory, directory mutation journal and organization versions. V36 adds enterprise review state/version and the legacy membership conversion. Both retain existing business rows. V36 uses UUID for migrated member IDs; the deployed MySQL 9.7 rejects MD5().

Invitation tokens, invitation/join lifecycle records and their existing capability/role selection workflow remain the original in-memory subsystem. Only the membership/assignment bridge is made durable here. A browser login flow, complete invitation authorization provisioning and independently deployed node failover require their own acceptance evidence. HTTP integration and real MySQL migration tests do not establish those outcomes.

## Live acceptance corrections (2026-10-15)

Ordinary organization readers see only their active assigned organizations. Tree/list responses filter unassigned units; a visible child whose parent is not visible becomes a tree root without revealing the parent's record. Detail, membership and organization-audit reads for an unassigned organization return404. The subject may read their own assignment/context audit. Organization administrators may read all units only while their current persisted organization-write grant remains effective; a stale write claim alone does not broaden visibility. Existing enterprise revision/If-Match semantics remain unchanged.

Creating an enterprise atomically inserts the creator's active member record and a tenant-scoped administrator role/binding. A synchronous EnterpriseCreated event allows the member and authorization modules to write their own records in the creation transaction, avoiding an enterprise-to-member/authorization dependency cycle. The initial role contains only organization read/write, member read/write, role read/write and capability read; it does not grant platform or other tenants' business permissions. A fresh PKCE login obtains the new membership and grants. Directory creation/member audit and authorization mutation/outbox records retain the creation requestId. GET `/api/v1/platform/enterprises/{enterpriseId}/audit` reads directory lifecycle audit under platform.enterprise.read.

POST `/api/v1/enterprises/{enterpriseId}/members` explicitly binds an existing active local login subject using `{subject, displayName, email}` and a required Idempotency-Key. It returns201, MemberDetail and ETag; unknown/inactive identities are400, duplicate membership409. A replay returns the original receipt without adding another member or audit entry. The endpoint requires enterprise.members.write and active tenant membership, grants no roles automatically, and never restores a disabled member. Role assignment remains a separate authorized action. Invitation acceptance retains its existing external identity bridge.

V37 replaces the capability table's global unique(code) with a null-safe unique index on `(scope, COALESCE(enterprise_id, ''), code)`. No columns or historical migration files change. This permits separate tenants to persist identical stable permission codes while keeping platform capability codes unique. Capability lookup, reload and duplicate detection use the same owner boundary; generated dynamic capability IDs are independent of the code. V36→V37 and creator login/onboarding run against real MySQL in EnterpriseOnboardingMySqlHttpTest.

Duplicate login usernames now return409/SUMMER_USER_CONFLICT with Request correlation, including unique-key conflicts observed at flush. No password or SQL exception details enter that response.

The historical organization journal uses one resourceId column for unit IDs, member IDs and subjects. Read authorization therefore checks unit ownership first and filters self-service assignment/context audit by event type and authenticated actor/member identity. A username equal to an organization ID does not grant that organization's audit. This needs no destructive journal rewrite or additional migration.
