# 独立管理权限，并分别授予菜单权限与接口权限

状态：已接受。用户于 2026-11-04 确认业务模型定稿，并确认真实 HTTP、MySQL/Redis、浏览器、双节点即时撤权及升级迁移测试边界。配套[技术方案](../specs/permission-management-spec.md)已形成；代码实现与历史迁移尚未开展。

## 权限、分组与角色

系统提供独立的权限管理功能，支持新建权限；权限组用于分组分类，每项权限直接归属且只归属一个权限组，授权关系关联具体权限。权限组支持多级父子结构，例如“业务管理→订单管理→订单查询”。同一权限组允许包含接口权限、菜单权限和数据权限，权限类型是各项权限自身的属性，不是分组的类型限制。例如“订单管理”组可同时包含进入订单管理的菜单权限、查询订单的接口权限及查询本部门订单的数据权限。调整权限所属分组或分组层级只改变分类，不改变已有授权；父组和子组都不是授权对象，不产生权限继承或隐式授予。接口不保留权限码，接口与权限不再视为同一对象。

需要明确授权的权限只授予角色，用户通过角色获得权限，授权路径为“用户→角色→权限”，不提供用户直接授予权限的配置。公开访问和登录访问仍按各自访问方式判定，不要求为其逐一分配角色。新方案不保留用户级显式拒绝，授权差异统一通过角色表达。现有用户拒绝规则须迁移为相应的角色授权配置，不能仅删除拒绝记录而扩大已有访问范围；技术方案规定按原有效授权结果转换为等价的收窄角色，不能等价转换的历史数据阻止切换，不自动放宽。这一选择不取消租户边界、资源策略上限或无授权默认拒绝。

## 访问方式与接口关联

访问方式定义在权限上，区分公开访问、登录访问和授权访问；接口资源不保存独立的访问方式属性。对于接口访问，公开方式允许匿名请求满足该权限的访问条件，登录方式要求有效登录，授权方式要求请求者获得相应有效权限。这是权限的访问方式维度，与权限控制的对象类型分开。新建权限默认采用授权访问，公开访问和登录访问必须显式选择，避免漏选访问方式时意外扩大访问范围。

同一个接口关联的权限必须采用相同的访问方式，不允许混合公开访问、登录访问和授权访问。此约束由权限与接口的关联配置校验保证，接口资源不增加访问方式字段；建立或变更关联、修改权限访问方式后的状态都必须满足该约束。选择禁止混用，是为了避免在任一满足规则下，一项公开或登录访问权限意外削弱同一接口其他权限所表达的访问要求。

接口权限与接口资源采用多对多关系：一项接口权限可以关联多个接口，同一接口也可以被多个接口权限关联。例如“查看订单”关联订单列表、详情及状态查询接口，“审核订单”也可关联同一个订单详情查询接口。这样不同业务权限可以复用接口资源。

接口路径或HTTP方法发生变化时，将其视为新接口资源，默认拒绝访问，由管理员重新建立权限关联，不自动继承旧接口的关联。例如从GET /orders改为POST /orders/query后，需要显式把新接口关联到相应权限；可以复用原有权限定义，不必仅因接口变化就重建权限或角色。采用这一规则以保持资源变更处理简单，避免接口用途变化后自动继承旧授权。

同一接口关联多个接口权限时，按任一满足（OR）判定接口的允许条件。对于采用授权访问方式的关联权限，主体拥有其中任意一项有效接口权限，即满足该接口的权限要求，无需同时拥有全部关联权限。例如只拥有“查看订单”或只拥有“审核订单”，均可满足上述订单详情接口的权限要求。该规则只确定接口权限的允许条件，不替代身份、租户、数据范围等其他适用检查；接口资源使用持久身份及包含完整匹配条件的定位键，具体契约见配套技术方案。

新扫描出来、尚未关联任何权限的业务接口默认拒绝访问，不因请求者已经登录而放行。管理员建立接口与权限的关联后，按所关联权限的访问条件判定；授权访问方式仍要求向主体完成相应授权。接口关联缺失不能作为公开访问或仅需登录的隐式标记。

## 菜单关联与导航

菜单权限与接口权限分别授权。授予“订单管理”菜单权限不会自动授予该页面使用的查询、审核等接口权限；菜单授权本身不足以允许接口调用。选择独立授权，是为了让菜单入口的配置与接口访问权之间保持明确边界，避免菜单的接口依赖变化隐式扩大已有授权；代价是管理员需要分别配置两类权限。

菜单权限与菜单采用多对多关联：一项菜单权限可以关联多个菜单，一个菜单也可以关联多项菜单权限。请求者满足其中任意一项有效关联菜单权限的访问条件，即具备该菜单的访问资格，无需同时满足全部关联权限。菜单启用状态、路由有效性等其他条件仍需满足。同一菜单关联的多项菜单权限必须采用相同访问方式，不能混合公开访问、登录访问和授权访问；建立或修改关联、修改权限访问方式后的状态都必须满足此约束。访问方式仍保存在权限上，菜单资源不增加独立的访问方式字段。

用户具有子菜单访问资格、但不具有已启用父菜单的页面访问资格时，父菜单仍作为不可点击的目录展示，使用户能够找到并进入有权限的子菜单。必要的已启用祖先目录采用同一规则；目录可见不授予父页面、兄弟菜单或接口的访问权，父页面路由仍按其自身菜单权限校验。此规则不绕过菜单停用，已禁用的父菜单不因此恢复其分支展示。选择这一规则是为了让导航层级不迫使管理员额外授予父页面权限。

## 数据范围

本次数据权限仅控制记录范围（行级权限），字段可见性、字段脱敏和字段编辑权限不纳入本次新增功能，留作后续独立扩展。单项数据权限只选择一个预设范围，不提供自定义条件、AND/OR条件组合或嵌套表达式配置，以保持管理模型简单；多项数据权限之间仍按已确认规则取并集。预设范围固定为五种：本人、本部门、本部门及下级部门、指定部门、当前租户全部。没有对应数据权限时仍为空范围，不自动套用任何预设。

“本人”依据每类业务资源预先确定的归属规则判定，不一律等同于记录创建人。例如订单可以按负责人、申请单可以按申请人确定归属；甲代乙录入且由乙负责的订单，在按负责人归属的资源中属于乙。权限管理只选择“本人”预设，不提供逐项配置归属字段或表达式的功能。

“本部门”采用主体在当前租户内所有有效任职部门的集合，不只采用当前选中部门，也不随当前部门切换而收窄。“本部门及下级部门”从这些有效任职部门分别向下展开并取并集，重叠部门去重；没有有效任职部门时，这两种范围为空。当前组织上下文的选择功能继续保留，但不作为这两种范围的唯一计算依据。

“指定部门”支持多选，一项数据权限可在当前租户内指定多个部门，例如财务部与审计部，无需按部门分别创建权限。部门清单是单一预设范围的配置，不引入自定义条件或表达式。范围仅覆盖明确选中的部门，选中父部门不自动包含下级部门；下级部门需要另行勾选，后续新增下级部门也不自动扩大已有指定部门范围。

数据权限按“业务资源＋操作＋数据范围”定义，同一业务资源的查询、修改等操作可以分别设置范围。例如查询订单允许本部门范围，修改订单只允许本人负责范围；查询范围不得自动成为修改范围。数据权限限制操作所能涉及的数据，接口权限仍单独决定相应接口的调用许可。

同一主体获得多项针对相同业务资源、相同操作的数据权限时，允许范围取并集。例如查询部门甲订单与查询部门乙订单的两项授权，可合并为查询两个部门订单的范围。合并结果仍受当前租户边界和资源策略上限约束，不混合不同资源或不同操作的范围，查询范围不能扩大修改范围。选择并集是为了使独立授予的允许范围能够累加。

对于纳入数据权限控制的业务资源，主体没有对应操作的数据权限时，可访问数据范围为空，即使已满足接口权限要求也不能访问任何数据。不自动授予本人、本部门或全部数据范围；资源策略上限不能替代缺失的数据授权。技术方案明确列表返回空集合与零总数，单条记录采用不可见语义，写入不得把未授权目标当作成功；既有策略须经等价性验证后切换。

## 变更生效

权限配置、资源关联及角色授权的变更，保存成功后立即对后续请求生效，无须重新登录，不增加草稿和发布步骤。例如撤销导出权限后，已登录用户的下一次导出请求应被拒绝；不能继续依据旧登录时的权限快照放行。保存成功以持久化事务提交为界，后端权限判定不能以旧令牌内容或前端菜单尚未刷新为由保留已撤销的权限。

## 与既有决策的关系

- 部分替代 [ADR 0030](0030-deny-unassigned-users-and-align-configurable-resource-grants.md) 中接口显式声明权限码、未声明时以 HTTP 方法和路由模板充当权限码的目标设计。新权限模型不沿用用户级显式拒绝；默认拒绝、租户隔离及审计等约束不因本决定取消。
- 部分替代 [ADR 0026](0026-use-versioned-route-menu-manifest.md) 中保留用户显式拒绝的规则，并明确菜单过滤与接口鉴权分别使用各自的授权关系。菜单 manifest 的发布、路由归属和企业覆盖安排不因本决定变更。
- 补充 [ADR 0028](0028-enforce-effective-configuration-scopes.md)：新权限模型中的数据范围按业务资源和操作区分，并收窄为单项权限选择一个预设范围，不暴露原结构化策略的条件组合配置。既有租户边界和资源策略上限不因这一简化取消，旧组合数据策略按技术方案等价转换；不能表达的策略成为切换阻断项。
- 补充 [ADR 0032](0032-persist-enterprise-members-and-organization-context.md)：保留当前组织选择及其有效性校验，新数据权限中的本部门范围使用同租户全部有效任职部门，不等同于单个当前组织上下文。
