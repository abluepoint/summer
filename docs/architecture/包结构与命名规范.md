## 已确认的包组织规则

架构取舍记录于 [ADR 0034](../adr/0034-organize-packages-by-responsibility-and-role.md)。

总原则：外层按职责，内层采用与职责匹配的统一分层。

- 外层按功能或能力职责组织，例如 `customer`、`dictionary`，不在应用根包横向汇总所有 Controller、Service 或 Repository。
- 职责包内部采用明确的层次组织；技术分层与领域分层按下列标准和模板选择。
- 不再以小功能规模为理由默认把 Controller、Service、Repository 及相关数据类型全部平铺在同一个职责包。
- 框架能力职责内部采用已确认的 `api/spi/internal` 划分；业务功能按已确认标准采用技术或领域分层。自动配置模块的具体分包继续按装配职责细化。
- 本规则不改变已确认的框架与产品归属，也不将业务实体或 Repository 提升为跨模块共享契约。

### 内层分层选择标准（已确认）

2026-10-20：确认简单 CRUD 与直接查询优先采用技术分层；具备聚合约束、状态流转或业务策略的功能采用领域分层。同一职责包选定一套主分层方式。技术分层使用 `controller/service/repository/model`，领域分层使用 `api/application/domain/infrastructure`；具体角色和依赖方向见下文模板。

《模块边界》和《整体架构》已同步 Customer 的目标分层说明；当前 Customer 实际结构仍按现状清单记录，尚未执行分包迁移。

### 框架能力模块内层划分（已确认）

2026-10-28：确认框架能力包采用“职责 + api/spi/internal”的内层划分，按实际需要建立子包，不要求每项职责都具备全部子包。

| 子包 | 职责 | 目标包名示例 |
| --- | --- | --- |
| `api` | 供应用调用的稳定契约及其必要数据类型 | `security.session.api` |
| `spi` | 供应用实现的稳定扩展接口及其必要契约类型 | `security.identity.spi` |
| `internal` | 框架内部实现，不作为应用的稳定依赖入口 | `security.identity.internal` |

`SummerIdentityStore` 的目标路径示例为 `com.abluepoint.summer.security.identity.spi.SummerIdentityStore`，所属构建模块为 `summer-security`；其余 Store 接口的职责子包见下文逐模块目标清单。自动配置继续归独立 `*-autoconfigure` 模块，负责条件装配、属性绑定和实现选择；Starter 不增加 Java 实现。

`internal` 是依赖边界约定，包名本身不会自动限制 Java 跨包访问。类型能否保持包可见、以及装配模块对内部实现的必要访问，应在后续依赖规则中明确；不能将所有 Java `public` 类型一概视为稳定 API。

### 类型文件组织（已确认）

当前 `AuthorizationModels.java`、`DictionaryModels.java`、`TaskModels.java` 分别包含 14、5、7 个包可见的顶层 record，属于同文件多个顶层类型，并非嵌套类容器。

2026-10-28：确认一个顶层类型一个同名文件，各类型归入实际所属的层和职责包；仅被单个实现使用的辅助结构可保留为私有嵌套类型。不再以 `*Models.java` 等文件聚集多个顶层类型。这是目标规则，现有类型文件本轮不拆分。

### 带操作的数据类型命名顺序（已确认）

当前 Customer 使用 `CreateCustomerRequest`、`CreateCustomerCommand`，Authorization 使用 `RoleCreateRequest`、`RoleUpdateRequest`；带操作的数据类型存在两种命名顺序。

2026-10-28：用户选择“资源 + 操作 + 用途”，例如 `CustomerCreateRequest`、`RoleCreateRequest`、`CustomerUpdateCommand`、`CustomerListQuery`。没有操作语义的视图或资源类型不强行加动词，例如 `CustomerView`。目标命名以本规则为准，现有动作前置的类型只列为调整项，本轮不改 Java 源码。

### 数据类型用途后缀（已确认）

2026-10-28：用户确认 `Request`、`Command`、`View`、`Entity` 及独立领域模型的命名规则，并确认 HTTP 查询输入使用 Request，Query 仅表示有必要独立定义的内部查询条件。按用途命名，不混用泛化的 `DTO/VO/PO` 后缀：

| 用途 | 后缀 | 命名示例 |
| --- | --- | --- |
| HTTP 输入（包括 GET 参数） | `Request` | `CustomerCreateRequest`、`CustomerListRequest` |
| 应用写入用例输入 | `Command` | `CustomerCreateCommand` |
| 必要时独立定义的内部查询条件 | `Query` | `CustomerListQuery` |
| 查询结果或展示数据 | `View` | `CustomerView`、`CustomerSummaryView` |
| 持久化实体 | `Entity` | `CustomerEntity` |

独立领域模型使用业务名称，例如 `Customer`；该规则不要求为每次层间传递创建重复的数据类型。查询执行组件统一使用 `QueryService` 后缀，`Query` 后缀保留给必要时独立定义的内部查询条件。

#### 查询条件与 HTTP 参数（当前事实与已确认目标）

当前 `CustomerListQuery` 包含 `page`、`size`、`active`、`sort`、`direction`、`projection`，这些值来自 GET 列表接口的 HTTP 参数。Controller 通过 `FieldValues` 取得经过参数契约处理的值，补默认值并转成枚举后构造该对象，再交给 Service 和 `CustomerQuery` 执行读取。当前没有独立的 `CustomerListRequest`。

它的当前职责是携带查询条件，不执行 SQL。与 HTTP 参数相比，该对象还表达默认值、类型化排序和分页约束；但现有列表场景中的字段基本一一对应，不能仅因增加分层就认定必须再造一份相同结构。

已确认：HTTP 输入统一使用 `Request`，包括 GET 参数；`Query` 仅用于确实需要与传输结构分开的内部查询条件，简单 CRUD 不强制同时建立 Request 与 Query。本规则不要求额外引入与请求一一对应的条件类型；具体跨层参数组织在逐模块设计中保持与选定分层一致。

### 查询执行组件命名（已确认）

2026-10-28：确认专用查询执行组件统一命名为“资源＋QueryService”，例如 `CustomerQueryService`。当前 `CustomerQuery` 持有 `JpaSqlTemplate` 并执行列表和计数查询，其目标类名为 `CustomerQueryService`；条件对象使用 `CustomerListQuery`，HTTP 输入使用 `CustomerListRequest`。这不改变 CustomerService 负责业务编排与事务、专用读取组件负责 SQL 的已有分工。不要求将同时承担读写编排的普通 Service 拆成两个组件；本轮只维护目标命名，源码与测试尚未改名。

### 稳定扩展接口归属（已确认目标）

2026-10-20：用户明确确认将六个 Store 稳定扩展接口归入 `summer-security`。包括 `SummerIdentityStore`、`SummerOAuthClientStore`、`SummerAuthorizationStore`、`SummerConsentStore`、`SummerKeyStore`、`SummerSessionStore`。能力模块拥有这些扩展契约，自动配置模块负责实现选择、Bean 条件装配及配置绑定；接口的职责子包见 Security 目标清单；六个默认实现归入能力模块 internal 已于 2026-10-28 确认。当前源码仍位于自动配置模块，本次只记录迁移建议，不改 Java 或构建配置。

当前 `summer-security-autoconfigure` 的 `security.autoconfigure.storage` 同时包含六个应用可实现的 `Summer*Store` 接口、默认实现及安全过滤组件。Sample 已直接导入这些接口，并在部分配置中直接导入过滤器及默认 Session 实现。

#### 默认安全实现的归属（已确认目标）

当前六个 `DefaultSummer*Store` 也位于自动配置模块：Identity、OAuthClient、Authorization、Consent 通过委托 Spring Security 接口完成适配，Key 持有 JWKSet，Session 继承 Servlet Session 的安全上下文仓储。2026-10-28 已确认这六个默认运行时适配实现归入 `summer-security` 各职责的 `internal`。

目标为运行时实现归 `summer-security` 各职责的 `internal`，自动配置模块只负责属性绑定、条件选择和 Bean 创建。这样能力行为可独立于 Boot 装配测试；实现类型为供装配访问而声明 Java `public` 时，也不因此成为应用稳定 API。本次不改 Java 源码或 Gradle 依赖。

Data JPA 中的 `SqlResultProjectionAdapter` 已使用包可见性隐藏实现；因此后续公共接口边界规范须区分 Java `public` 可见性、应用扩展契约及装配可访问性，不能仅按修饰符判定稳定 API。

## 包、类型和目录命名细则

- Java 根命名空间沿用 `com.abluepoint.summer`。Java 包使用小写，职责名沿用现有 `auditledger`、`systemparameter` 等写法；本次不额外改为多个新职责包。Gradle 模块保持 `summer-<capability>[-autoconfigure|-starter]` 的现有名称，前端保持 `summer-ui`。
- Java 类型使用 UpperCamelCase，同名 `.java` 文件；方法、字段和局部变量使用 lowerCamelCase。既有 `Summer*` 框架品牌前缀保留，不为所有业务类型强加前缀。新类型以职责和用途命名，不用 `Manager/Helper/Util/DTO/VO/PO` 掩盖已能明确的角色。
- `Controller` 表示 HTTP 入口，`Service` 表示用例编排或业务服务，`QueryService` 表示专用查询执行，`Repository` 表示仓储契约或持久化接入。框架扩展接口以真实能力命名，如 `MessageResolver`、`RequestLogSink`、`SummerIdentityStore`；不机械添加 `I` 或 `Impl`。
- `Request/Command/Query/View/Entity` 按前文用途使用，并保持“资源＋操作＋用途”的顺序。不能只按含有 Query 字样就批量改名，须先区分条件对象与执行组件。独立领域对象使用业务名，其持久化适配使用 Entity 后缀。
- `AutoConfiguration/Properties` 归独立装配模块，业务功能配置归其自身 `configuration` 或领域层的 `infrastructure.configuration`。不新建顶层 `shared/dto/support/util` 来收容缺少归属的类型。
- UI 业务目录延续现有小写及连字符形式，例如 `auth-users`、`system-parameters`；页面入口保持 `index.tsx` 或已有路由入口。业务请求与类型文件用 `api.ts/types.ts`，组件和 Hook 依已有工程约定采用组件名及 `useXxx`；不为统一 Java 包名而重命名前端路由或目录。

### 安全接入预整理（#147）

#147 在现有包中完成安全接入边界整理，尚未实施 Store 或运行时类型迁包：

- 自动配置提供具名 `summerResourceServerSecurity` Bean，契约为 Spring `Customizer<HttpSecurity>`。应用自建资源链按名称注入并调用一次，再定义自身请求匹配、授权与 CSRF 策略。该接入只组合 Bearer/Session 隔离、安全上下文仓储、Session 创建策略、空请求缓存及资源认证/错误处理，不承载应用授权规则。
- 默认资源链与 Sample 监控链使用同一装配入口；每条链使用各自的 `HttpSecurity`，保留原有链顺序、授权规则及 CSRF 策略。装配仍选择应用提供的 `SecurityContextRepository` 与 `JwtAuthenticationConverter`，并允许应用按 Bean 名覆盖该组合入口。
- `SummerSecurityContext.hasBearerCredentials(HttpServletRequest)` 是会话与长连接消费方需要的最窄身份路径判定。它只识别 Bearer 凭据路径，包含格式错误的 Bearer 前缀，不校验或解析令牌；原有判断算法移至此处，过滤器、仓储及 Sample 会话消费者统一调用。
- `MonitoringSecurityConfiguration`、`SessionController`、`SessionStreamAccess` 已消除对目标 internal 安全仓储、过滤器、默认 Session 与安全 HTTP 处理器的依赖。模块架构测试约束该范围；Key 审计中对默认日志实现的既有引用由后续安全/Key 迁移继续处理。
