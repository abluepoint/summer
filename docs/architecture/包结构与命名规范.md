# summer4 包结构与命名规范

本规范落实 [Issue #146](https://github.com/abluepoint/summer/issues/146) 与 [ADR 0034](../adr/0034-organize-packages-by-responsibility-and-role.md)。迁移前盘点基于 summer4 的既有工作区；实施范围、实际运行证据及尚未验收项见 [迁移验收](../acceptance/summer4-package-refactor.md)。Java 包全名有明确变化，不承诺旧包源码或二进制兼容；HTTP、JSON、权限与持久化契约保持。

## 组织与依赖

外层按职责，内层采用与职责匹配的一种主分层。保持 15 个 Gradle 模块和独立 Summer UI；不新增 shared/core/DTO 模块，不因分包裁定产品归属。

| 区域 | 实际分层 | 依赖规则 |
| --- | --- | --- |
| 框架能力 | 职责下按需设置 api、spi、internal | 应用使用 API/SPI；装配可访问必要 internal；能力不依赖装配/Starter/业务 |
| 技术职责 | controller、service、repository、model | Controller 调用 Service；Service 编排事务及 Repository/QueryService；Repository 不反向依赖端点 |
| 领域职责 | api、application、domain、infrastructure | API 调用 Application，Application 使用 Domain，Infrastructure 适配端口；Domain 不依赖其它三层 |

技术职责的数据按 request/command/query/view/entity 分类，配置、初始化、异常按需放 configuration/bootstrap/exception。领域职责的数据与异常归其实际层，不建贯穿四层的 model/support。只为真实业务需要设置端口，不把 Spring Data Repository 当 Domain，不为层数复制同构输入。根应用包只保留启动和全局装配。

Java public 只解决必要的跨包访问，不自动代表稳定 API。Modulith 用类型级 NamedInterface 声明实际跨职责契约，消费者以 module::interface 明确依赖；不开放整个模块来绕过检查。Domain 上 NamedInterface 仅为边界元数据，不引入运行时 Spring、HTTP 或 JPA 协作。

## Sample 的 30 项职责

| 分层 | 职责 |
| --- | --- |
| 技术分层（6） | cache、customer、observability、operations、resilience、statistics |
| 领域分层（24） | agent、application、auditledger、authorization、bff、configuration、connection、delegation、dictionary、enterprise、identity、invitation、key、mcpauthorization、member、menu、organization、physicalconnection、plugin、realtime、release、resource、systemparameter、task |

Controller、持久化实体或框架适配器不能仅搬到 Domain。领域层须实际拥有相关校验、状态转换、版本/授权范围规则和必要端口。查询/写入事务及外部设施留在对应层；每个职责的执行证据按实施票与最终验收记录。

customer 和 operations 继续是 Sample 参考职责。既定 AICT IAM、BFF、审计、物理连接及发布控制面归属沿用 [模块边界](模块边界.md)；本次不迁出产品。cache、configuration、dictionary、key、menu、observability、plugin、realtime、resilience、resource、statistics、systemparameter、task 这 13 项的最终产品归属仍未另裁定，不能因其分层自动扩张框架或 AICT。

## 类型与命名

一个顶层类型一个同名 Java 文件；私有、单实现辅助结构可保留嵌套形式，公开嵌套契约按实际消费用途判断。类型使用 UpperCamelCase，成员使用 lowerCamelCase，包使用小写；保留既有 Summer 品牌前缀。带操作的数据类型统一“资源＋操作＋用途”，不以泛化 DTO/VO/PO、Helper/Manager 隐藏职责。

| 用途 | 命名 | 约束 |
| --- | --- | --- |
| HTTP 输入，包括 GET 条件 | Request | 不因查询参数来自 HTTP 就命名为 Query |
| 写用例输入 | Command | 有实际用例意图才独立定义 |
| 内部查询条件 | Query | 只为确有独立语义的条件定义，不复制同构 Request |
| 展示与读取结果 | View | 字段与既有 JSON 契约保持 |
| 持久化对象 | Entity | 保持物理表/列、默认实体名及查询引用 |
| 独立领域模型 | 业务名称 | 不带传输或持久化实现责任 |
| 专用查询执行组件 | QueryService | 与查询条件类型区分，不机械拆普通读写 Service |

Customer 已采用 CustomerCreateRequest、CustomerUpdateRequest、CustomerCreateCommand、CustomerUpdateCommand、CustomerEntity 和 CustomerQueryService。列表沿用 CustomerListRequest，不另造同构 CustomerListQuery；Service 负责事务，QueryService 负责 SQL、读取配置和查询指标。CustomerAuditQuery 保留真实内部审计筛选语义。

重命名 record 或迁包时检查 ETag、内容指纹和幂等文本是否依赖 toString；保留既有业务版本语义。已应用 Flyway 迁移不得改写，也不为包名增加数据库迁移。Quartz 持久化任务类变化通过既有任务 key 的作业更新保留触发器。接口资源历史绑定只将清单中精确类型迁移视为同一拥有者，不修改历史快照，真实处理器替换仍须显式权限。

## Summer UI

延续 Arco 基线、现有路由与国际化。业务仍按 src/pages/<职责>/ 集中，私有请求、类型、组件和 Hook 按需组织。认证与菜单分别拥有 src/auth、src/menu 的协议与生命周期。

| 通用区域 | 责任 |
| --- | --- |
| src/api/client.ts | 业务 HTTP 调用适配 |
| src/api/envelope.ts | 成功响应解包与失败分类 |
| src/api/errors.ts | SummerApiError 及错误元数据 |
| src/api/types.ts | 跨业务响应与失败类型 |

公共 HTTP 不依赖页面类型；业务端点和业务数据留在各自功能。Customer 的路由、表单、删除确认及列表页码恢复不抽入公共层。保留 requestId、非2xx、空响应、认证恢复且不自动重放写入的行为；OAuth2/OIDC、CSRF、文件传输遵守原始协议。菜单继续按上下文和返回事件刷新，不恢复定时轮询。

## 检查入口

verifyModuleBoundaries 验证 15 模块注册、依赖与环；ModulithArchitectureTest 验证实际 Sample 契约图；CustomerArchitectureTest 验证事务/SQL/指标归属；PackageArchitectureTest 验证所有职责分层、Domain 方向、应用不消费 internal、技术层方向、Starter 无实现、唯一框架目标及顶层类型文件组织。

结构检查不能替代实际行为。能力/装配、Sample HTTP/持久化、UI行为/类型/lint/build、真实浏览器及现有原生依赖测试须按实际执行记录，分别报告缓存、失败和跳过，不用成功构建冒充页面验收。
