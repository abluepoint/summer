## Sample 目标组织

2026-10-28 已确认全部 30 个职责包的目标分层：6 项技术分层、24 项领域分层，逐包依据与归属见 [包结构与命名规范](包结构与命名规范.md)。分层选择不改变既有产品边界，源码尚未迁移。

2026-10-28 已确认领域分层模板：复杂职责包内部使用 api/application/domain/infrastructure；API 调用 Application，Application 使用 Domain，Infrastructure 实现领域端口，Domain 不反向依赖其它层。HTTP 请求和 JPA 实体分别归传输层和持久化适配层，避免为分层创建无独立职责的重复模型。

2026-10-28 已确认技术分层模板：功能职责包内采用 controller/service/repository/model，并将数据类型按 request/command/query/view/entity 细分；功能配置、示例初始化分别归 configuration/bootstrap。2026-11-02 按 [ADR 0035](../adr/0035-reuse-summer-exception-for-application-failures.md) 收窄异常安排：专用 exception 包仅用于字段校验，子类统一继承 SummerException，其余自有异常直接使用 SummerException。只建立实际需要的包。详细类型对照与逐职责分层清单见 [包结构与命名规范](包结构与命名规范.md)。

- `customer` 拥有实体、Repository、业务事务、查询、读模型、Style 和受保护端点。2026-10-20 确认外层按职责、内层分层：简单 CRUD 与直接查询采用技术分层，有聚合约束、状态流转或业务策略时采用领域分层，同一职责包保持一种主分层方式。Customer 数据类型仍归 Customer 功能范围，按对应层组织，不恢复跨功能 `shared` 包或额外 DTO/API 构建模块；这属于目标结构，当前代码尚未迁移。具体规范见 [包结构与命名规范](包结构与命名规范.md)。
- `CustomerService` 负责业务编排和事务；当前 `CustomerQuery` 集中拥有 SQL resource、`JpaSqlTemplate` 和查询指标，其已确认目标类名为 `CustomerQueryService`。既有 Customer 架构测试约束当前分工；目标改名尚未实施。
- `operations` 提供公开运行信息，不引用 Customer 内部实现。
- 启动类和全局配置留在应用根包。Customer username 改造不改变这些职责。

## 检查能力与限制

根构建中的 `moduleDefinitions` 是 15 个模块的注册表，同时记录模块职责和允许的 Gradle 项目依赖。`verifyModuleBoundaries` 在根 `check` 中执行以下门禁：

1. `settings.gradle.kts` 的项目集合必须与注册表一致；
2. 根目录下带有 Gradle 构建脚本的模块目录必须已登记；
3. 每个项目依赖只能指向其允许的项目；
4. 依赖图不能包含环，并输出完整的环路径。

因此新增项目、漏登记目录、非法依赖和循环依赖都会在 CI 中失败，并给出模块名称及允许依赖列表。模块注册表的循环检测包含正例和无环反例断言；`ModulithArchitectureTest` 通过 `ApplicationModules.verify()` 检查 Sample 包级边界，并在当前显式注册断言中检查 `systemparameter` 已注册。上述检查分别验证 Gradle 构建图和 Sample 运行时包图，不能替代 Java 包导入、第三方依赖审计或产品迁移验收。

`ModulithArchitectureTest` 对当前 Sample 执行 `ApplicationModules.verify()`；`CustomerArchitectureTest` 检查 Customer 事务、SQL 与指标依赖。它们验证可检测的结构，不验证“某个包是否应该属于框架”，也不验证浏览器 OIDC 与部署隔离。

演进时新增能力须同时更新 settings、平台、依赖白名单、条件装配、文档和验收。跨应用通过契约交互；跨应用不共享实体或 Repository，不因为一个消费者就建立通用共享模块。
