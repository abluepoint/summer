# Summer 4 模块边界

本文件区分当前构建事实和目标应用归属。总览见 [整体架构](整体架构.md)，迁移状态见 [现状与目标差异](现状与目标差异.md)。

## Gradle 模块与允许依赖

下表列出运行时/编译期的项目依赖；所有 Java 子项目另引入 `summer-dependencies` 平台约束。平台约束不是运行时调用关系。

| 模块 | 职责 | 允许的其他项目依赖（不含平台） |
| --- | --- | --- |
| `summer-dependencies` | Boot/Cloud/Modulith BOM 与 Summer 发布版本约束 | 无运行时项目依赖；constraints 覆盖下方 13 个库，不含 Sample |
| `summer-common` | 稳定错误、消息与响应契约 | 无 |
| `summer-mvc` | 参数、校验、请求关联、响应与错误 HTTP 适配 | common |
| `summer-data-jpa` | 实体基类、Repository、SQL template、窄化结果投影 | common |
| `summer-security` | 安全主体访问、401/403、结构化安全审计 | common |
| `summer-common-autoconfigure` | Common 条件装配 | common |
| `summer-mvc-autoconfigure` | MVC 条件装配 | common、mvc |
| `summer-data-jpa-autoconfigure` | Data JPA 条件装配 | common、data-jpa |
| `summer-security-autoconfigure` | Security 配置与安全过滤链装配 | common、security |
| `summer-common-starter` | Common 接入 | common-autoconfigure |
| `summer-mvc-starter` | MVC 接入 | common-starter、mvc-autoconfigure |
| `summer-data-jpa-starter` | Data JPA 接入 | common-starter、data-jpa-autoconfigure |
| `summer-security-starter` | Security 接入 | common-starter、security-autoconfigure |
| `summer-boot-starter` | 聚合接入与 Actuator | 四种能力 starter |
| `summer-sample` | 参考应用和集成验证 | boot-starter、data-jpa |

表中简写均带 `summer-` 前缀。以 [settings](../../settings.gradle.kts)、[根构建](../../build.gradle.kts) 和各模块 `build.gradle.kts` 为事实来源。

能力模块不得依赖 autoconfigure、starter 或 sample；MVC/Data/Security 不横向引用彼此实现，稳定公共契约归 Common。各 starter 没有 Java 实现。聚合 starter 不拥有业务代码。UI 不成为 Java 子项目，外部 IAM/BFF/连接服务不能被框架反向依赖。

四个能力模块按职责区分 api（应用调用）、spi（应用实现扩展）和 internal（内部实现），只建立实际需要的包。所有旧/新全名与目标模块见 [81 类型迁移对照](framework-type-migration.tsv)。

- Common 保持 error、message、response 窄边界。
- MVC 使用 parameter、request、response、error、logging 五项职责，不再横向汇集 annotation/filter/support。
- Data JPA 使用 persistence 与 query。窄投影适配器归 query.internal，不扩展为通用映射 API。
- Security 使用 identity、oauth2、key、session、audit、access。六个 Store SPI、六个 Default Store 及其它运行时类型均归能力模块；自动配置仅保留三个装配/属性/选择校验类型。企业、成员、业务策略及产品审计账本仍归应用。

应用只消费框架 API/SPI。具名 ResourceServerSecurity 组合 Spring 安全链，不作为全局 Customizer 参与 OAuth 链配置；实际实现和 fallback 选择留在装配中。Java public 不自动等于稳定接口。

## Sample 分层

全部 30 职责按 [规范](包结构与命名规范.md) 落地：cache、customer、observability、operations、resilience、statistics 采用技术分层，其余 24 项采用领域分层。分层不改变产品归属，不执行产品迁出。

技术职责使用 controller/service/repository/model，并按需设置 configuration/bootstrap/exception；model 按 request/command/query/view/entity 分类。领域职责使用 api/application/domain/infrastructure；API 调用 Application，Application 使用 Domain，Infrastructure 适配真实端口，Domain 不反向依赖其它三层，不拥有 HTTP Request 或 JPA Entity。

- CustomerService 负责事务与业务编排；CustomerQueryService 集中拥有 SQL resource、JpaSqlTemplate 与查询指标。HTTP 列表输入是 CustomerListRequest，没有为了分层复制同构 Query。
- 数据与异常归实际职责/层；只为业务需要定义端口，不恢复 shared 实体/DTO 模块。
- 类型级 NamedInterface 只暴露实际跨职责契约，消费者以 module::interface 明确依赖。Domain 的 NamedInterface 是边界元数据，运行时框架及外层协作仍禁止。
- 启动类和全局配置留在应用根包。模块检查不是独立产品部署或浏览器验收证明。

## 当前 Sample 中的产品代码

Sample 保持 30 个职责。以下为已确认的产品归属清单；未另裁定的 13 项见 [包结构与命名规范](包结构与命名规范.md)，分层落实不表示对应产品已经完成验收：

| 当前包 | 目标归属 | 迁移约束 |
| --- | --- | --- |
| `customer`、`operations` | Summer Sample | 保留，作为框架参考与验证 |
| `identity`、`enterprise`、`member`、`organization`、`invitation` | AICT IAM | 会话快照、企业/成员/组织/邀请规则归产品 |
| `application`、`authorization`（含 policy）、`agent`、`delegation` | AICT IAM | 注册、权限、Agent 与委托规则归产品 |
| `connection`、`mcpauthorization` | AICT IAM 控制面/显式连接契约 | 分离目录安全投影、授权许可与物理连接端口 |
| `auditledger` | AICT 审计产品能力 | 迁移实体、outbox、SQL、保留策略与测试 |
| `bff` | AICT BFF | Product Session 与服务器端换票不进入 Summer UI |
| `physicalconnection` | AICT 连接服务执行面 | 迁出直接依赖 IAM Java 实现的调用，落到显式远程契约 |
| `release` | AICT 运维/发布控制面 | 产品发布门禁不成为框架运行时 API |

源码还显示 `delegation` 使用 `mcpauthorization` 的审批 Interface，`physicalconnection` 直接调用 `auditledger`、`connection`、`mcpauthorization`。同进程 Java 调用不能当作已经实现独立连接服务部署的证据。迁出需处理这些 seam，并携带资源、配置和行为测试。

## 检查能力与限制

根构建中的 `moduleDefinitions` 是 15 个模块的注册表，同时记录模块职责和允许的 Gradle 项目依赖。`verifyModuleBoundaries` 在根 `check` 中执行以下门禁：

1. `settings.gradle.kts` 的项目集合必须与注册表一致；
2. 根目录下带有 Gradle 构建脚本的模块目录必须已登记；
3. 每个项目依赖只能指向其允许的项目；
4. 依赖图不能包含环，并输出完整的环路径。

因此新增项目、漏登记目录、非法依赖和循环依赖都会在 CI 中失败，并给出模块名称及允许依赖列表。模块注册表的循环检测包含正例和无环反例断言；`ModulithArchitectureTest` 通过 `ApplicationModules.verify()` 检查 Sample 包级边界，并在当前显式注册断言中检查 `systemparameter` 已注册。上述检查分别验证 Gradle 构建图和 Sample 运行时包图，不能替代 Java 包导入、第三方依赖审计或产品迁移验收。

`ModulithArchitectureTest` 对当前 Sample 执行 `ApplicationModules.verify()`；`CustomerArchitectureTest` 检查 Customer 事务、SQL 与指标依赖。`PackageArchitectureTest` 另外检查全部 30 职责的实际分层、Domain 无反向及运行时框架依赖、应用不消费框架 internal、技术层方向、Starter 无实现、81 个原框架类型的唯一目标，以及每个顶层类型一个同名文件。它们验证可检测的结构，不验证“某个包是否应该属于框架”，也不验证浏览器 OIDC 与部署隔离。

演进时新增能力须同时更新 settings、平台、依赖白名单、条件装配、文档和验收。跨应用通过契约交互；跨应用不共享实体或 Repository，不因为一个消费者就建立通用共享模块。
