# 权限独立管理与资源关联授权技术方案

业务模型已于 2026-11-04 确认定稿；真实 HTTP、真实 MySQL/Redis、浏览器、双节点即时撤权及升级迁移测试边界已确认。本文是待实施规格，不表示功能已经实现或验收通过。US 为用户故事，D 为实施决定，T 为测试组，AC 为验收项。

## Problem Statement

管理员需要在系统中独立创建、分类和授予权限，而不是依赖开发人员在接口上声明权限码。当前实现把接口权限注解、HTTP 方法与路由模板生成的权限码、Capability、角色、菜单和数据策略混合使用：接口声明、服务内硬编码校验及菜单绑定需要同步，管理员配置并非唯一业务授权来源。

现有目录虽然能够发现接口，但接口描述仍携带权限码；现有请求拦截器主要处理 JWT 主体，安全过滤链又统一要求登录，不能仅通过新增一个权限配置页面就正确支持公开、登录和授权访问。菜单还受祖先权限过滤；数据范围允许组合表达式和用户拒绝，超出本次确认的简单模型。旧登录状态、节点内存投影和异步事件也不能成为撤权后继续放行的依据。

目标是让管理员能够理解“用户因哪个角色、哪项权限、哪条资源关联获得访问资格”，独立维护菜单、接口和数据权限，并在保存后对后续请求生效。迁移必须保留既有租户隔离和访问限制，不能因取消旧权限码或用户拒绝而扩大授权。

## Solution

建立统一的 Permission 管理模型，类型固定为接口权限、菜单权限和数据权限。Permission group 支持多级父子分类，同组可以混合三类权限，每项权限直接归属且只归属一个组；组不是授权对象，不产生继承。需要明确授权的权限仅通过“用户 → 角色 → 权限”授予，不支持用户直接授权或用户级显式拒绝。

公开、登录、授权是权限自身的访问方式，默认授权访问。接口和菜单只作为资源与相应类型的权限关联，均支持多对多和任一满足；同一资源关联的权限访问方式必须一致。接口不保留权限码或访问方式。未关联权限的业务接口默认拒绝，接口路径或 HTTP 方法变化后视为新接口，管理员重新建立关联。

菜单授权与接口授权相互独立。用户有子菜单访问资格时，已启用但无页面访问资格的祖先只作为不可点击目录展示，不授予祖先页面或兄弟菜单权限。

数据权限按“业务资源＋操作＋一个预设范围”定义，只控制记录范围。五种范围为本人、本部门、本部门及下级部门、指定部门、当前租户全部。单项不支持条件组合，多项有效数据权限在同资源、同操作下取并集，并与租户边界、资源策略上限相交。没有对应数据权限则范围为空。

保存成功后，新配置立即用于后续请求，无需重新登录；前端展示、Token 中的旧权限以及事件通知的延迟均不能替代后端当前授权判定。

## Implementation Decisions

### D-01：实施范围与模块边界

在现有 Summer Sample、Summer UI、Summer Security 及其自动配置能力上演进。Sample 负责权限管理、持久化、接口目录、菜单投影、企业成员和数据资源接入；UI 负责管理交互与导航；Security 提供认证后统一授权的适配契约，自动配置负责接入现有过滤链。复用既有审计、outbox 和版本传播设施，不另建权限服务或另一套身份系统。所有自有业务接口及相应消费入口都必须纳入迁移盘点，不能只改权限管理接口自身。

### D-02：授权域、标识与唯一来源

沿用平台与企业的边界。每次判定先解析一个可信授权域；企业域包含明确 enterpriseId，平台域不能由普通企业参数伪装。权限、分组、角色、绑定、版本及幂等记录都带所属域，禁止跨域关联或取并集。共享接口目录可被不同域引用，但运行时只读取当前域的关联；同一接口或菜单的访问方式一致性也在其有效授权域内完整校验，不能混入其他租户权限补足访问条件。

Permission 使用不可变 permissionId；保留权限实体自己的 code 作为域内唯一的稳定业务引用，名称和说明可编辑。code 不是接口资源属性，也不是业务接口中的硬编码鉴权条件。跨域可存在同名或同 code 权限，所有查找必须带域。

### D-03：持久化模型

以新增迁移演进已有存储，不修改已发布迁移。建议逻辑模型如下，物理命名遵循现有数据库约定：

| 模型 | 核心数据与约束 |
| --- | --- |
| Permission | permissionId、所属域、code、name、description、type、accessMode、groupId、status、version；type 创建后不变，groupId 必填；同域 code 唯一 |
| Permission group | groupId、所属域、parentGroupId、name、sortOrder、version；单父节点、无环；权限只直接归属一个节点 |
| Interface resource | resourceId、稳定应用/来源标识、HTTP 方法、规范化路由模板、匹配条件、发现版本、状态及处理器溯源；无 permissionCode、无 accessMode |
| Resource association | 所属域、permissionId、资源类型、resourceId、版本；域与资源边界一致，关联对唯一；接口权限只关联接口，菜单权限只关联菜单 |
| Role permission | 所属域、roleId、permissionId；关联对唯一；用户仅保留角色绑定，无直接权限授予或拒绝列表 |
| Data permission detail | permissionId、dataResourceKey、action、scopePreset；每项数据权限一份详情 |
| Selected department | permissionId、departmentId；唯一、同租户，仅用于指定部门范围 |
| Authorization revision | 所属域及单调递增 revision；所有影响有效授权的变更共同推进 |
| Mutation receipt / audit / outbox | 幂等请求指纹、原始结果、主体与请求关联、变更版本及事件；与业务变更同事务持久化 |

复用现有角色、用户、成员、组织和菜单身份，避免重建身份关系。外键或等价持久化校验必须涵盖所属域；关联不能仅靠无域的字符串 code。

### D-04：权限组仅用于分类

支持多级、多类型混合及排序，父节点可直接容纳权限和子组。移动权限或组只改变分类；禁止环、跨域父节点和失效引用。组树查询可聚合展示后代权限，但不产生祖先授权、权限继承或动态角色绑定。角色页面按组勾选只是对当时具体权限集合的批量选择，保存 permissionId 清单；未来新增或移动到该组的权限不自动进入旧角色。

### D-05：权限定义及访问方式

type 固定为 INTERFACE、MENU、DATA；accessMode 固定为 PUBLIC、AUTHENTICATED、AUTHORIZED，默认 AUTHORIZED；status 沿用启用和停用的明确状态。PUBLIC 表示该权限条件不要求主体登录，AUTHENTICATED 要求真实有效身份，AUTHORIZED 要求当前有效角色持有该权限。三种方式均不是绕过资源自身业务限制的开关。

每项权限选择一个组。修改名称、说明或分组不改变身份与授权；修改访问方式、状态、资源关联或数据详情属于有效授权变更。权限创建或保存不自动授予创建者、当前组或任何角色。

### D-06：接口身份与扫描生命周期

保留自动发现与目录版本能力。采用持久化 resourceId，并以稳定来源/应用标识、HTTP 方法、规范化路由模板及完整匹配条件构成资源定位键；包含必要的参数、请求头、内容类型和版本条件，不能只比较 URL 文本。定位键使用确定性序列化，不依赖 Map 字符串输出；重复扫描同一定位键不产生重复资源。

权限通过关联表引用 resourceId。路径或方法变化产生新资源，默认无关联；允许管理员显式将其关联到原权限，不自动复制旧关联。匹配条件变化不得错误合并不同接口。消失资源保留历史和失效状态，不物理覆盖身份。现有处理器替换防复用保护由资源版本、处理器溯源和显式重新确认关联接续，不能再要求添加权限码来解除保护。Java 实现名称仅是溯源证据，不能取代完整请求资源定位。

### D-07：统一资源关联及并发不变量

接口和菜单分别与各自权限多对多关联。运行时在当前授权域中，满足任一有效关联权限即满足该资源的权限条件；没有匹配项则不产生访问资格。对同一接口、同一菜单，全部现存关联权限的 accessMode 必须一致，包含暂时停用的权限，避免重新启用时引入冲突。

新增/替换关联、批量编辑、权限访问方式修改、重新启用及迁移切换使用同一校验。按确定顺序锁定受影响的域内资源关联控制记录，读取当前关联与权限状态后写入；共享控制记录只保存版本和锁定身份，不保存资源 accessMode。多资源修改必须全成或全败，不能检查通过后再无锁写入。

### D-08：一个统一的请求授权判定入口

复用 HTTP 请求授权边界，以统一判定服务接入 Spring Security 的 AuthorizationManager 扩展，并与 MVC 实际匹配资源校验配合。输入为可信主体/匿名状态、授权域、实际资源身份与请求上下文；输出为允许或拒绝、原因和授权版本。不得仅对 JwtAuthenticationToken 执行，也不得让会话或匿名请求绕过。

过滤链必须支持动态 PUBLIC 规则，不能继续在所有业务请求前无条件要求 authenticated；同时不能把整个业务路径设为无条件 permitAll。前置匹配必须复用框架实际映射语义和目录完整条件，最终处理器与资源身份不一致、未注册适配器或无法可靠解析时失败关闭。保留协议、静态资源、回调及基础设施的专属链路与分类；HTTP 扩展入口通过同一判定契约适配，不创建按字符串前缀放行的旁路。

### D-09：移除权限码耦合而非只删除注解

从接口描述、接口管理契约和接口方法中去掉权限码，并清理路由自动生成权限码的授权用途。替换沿请求路径依赖固定业务权限码的注解、方法表达式及服务校验，使管理员配置的资源关联真正成为业务权限依据；非 HTTP 内部业务入口如有独立授权需求，调用同一判定服务并提供明确业务资源/操作上下文。

数据资源键、操作名和接口身份不是权限码，可以作为受控资源元数据存在。OAuth scope、身份有效性、企业成员状态、会话撤销、CSRF、PKCE 和协议原生响应继续承担各自职责；OAuth scope 不能替代角色授权，业务权限也不扩大客户端原有委托边界。无效 Bearer 凭据不能自动降级为匿名以利用 PUBLIC 规则。

### D-10：角色授权与权限组、旧权限包分离

有效角色权限按集合累加，角色及用户绑定必须属于当前域并处于有效状态。新接口只接受角色的 permissionId 清单和用户的 roleId 清单，不接受用户直接 permissionIds 或 deniedCapabilityCodes。权限组不进入运行时授权关系。

旧 Capability bundle 不等于 Permission group。其授予内容在迁移时按有效版本展开成明确角色权限关系，旧包版本历史保留作审计，不把旧 bundleId 转换成动态组授权。

### D-11：菜单资源与导航投影

保留现有版本化 menu manifest、稳定 menuId、前端组件映射和企业布局覆盖。manifest 描述导航资源，不再以单个 capabilityCode 作为授权来源；权限关联通过统一关联管理维护。前端不上传组件实现或鉴权表达式。

可见投影区分页面访问资格与目录可见性。先计算已启用菜单的实际资格，再补齐必要的已启用祖先目录；无页面资格的祖先标记为仅导航、不可点击，路由守卫仍拒绝进入其页面。禁用祖先不自动恢复子树；目录补齐不授予兄弟菜单或接口权限。详情页等无菜单行路由必须有明确所属页面资源映射，不能用任意 URL 前缀推定授权。

### D-12：菜单刷新与前端动作展示

沿用登录初始化、身份/租户变化、窗口 focus、页面恢复可见和管理保存后刷新的策略，不新增定时轮询。保留跨租户迟到响应丢弃、失败清除旧权限、相同清单不重建页面和表单保护。

菜单资格、目录可见与业务动作能力分别消费；按钮可使用后端计算的接口操作资格提示，但隐藏按钮不是安全边界。页面在远端撤权后可能尚未刷新，后端下一请求仍必须拒绝，前端收到拒绝后收敛显示。

### D-13：数据资源接入契约

为已纳入数据权限控制的业务资源建立受控注册描述，包括资源键、支持操作、租户归属、本人归属规则、部门归属规则及对应查询/写入适配器。本人规则按业务资源预先确定，例如负责人或申请人，不在权限管理中配置字段或表达式。

复用既有数据范围服务的预览、JPA 条件及绑定 SQL 谓词能力，接入权限模型时只暴露五种预设。资源字段映射必须由受信任的应用注册，客户端不能提供 SQL、字段名、表名或任意表达式。缺少必要映射的资源不得宣称已受数据权限保护，也不能用全量读取作为回退。

### D-14：五种数据范围的精确定义

| 预设 | 判定规则 |
| --- | --- |
| SELF | 当前有效主体按资源归属规则匹配的记录；无主体或归属不成立则为空 |
| DEPARTMENT | 当前租户内主体全部有效任职部门对应的记录，与当前选中部门无关 |
| DEPARTMENT_AND_DESCENDANTS | 从上述全部有效任职部门在当前有效组织目录中展开下级并去重；不跨租户，不因同名部门串域 |
| SPECIFIED_DEPARTMENTS | 管理员明确选择的同租户有效部门集合，支持多选；不自动包含下级，未来新增下级不自动进入范围 |
| TENANT_ALL | 当前可信租户内全部记录，仍受资源策略上限及业务约束限制 |

新建或替换指定部门范围必须选择至少一个有效部门；其他预设不得夹带指定部门列表。已配置部门后来失效时不继续贡献范围，也不退回其他范围。匿名或缺少任职的主体不能通过请求参数制造 SELF 或部门范围。

### D-15：数据权限的有效集合与组合

按当前授权域、dataResourceKey 和 action 选择有效数据权限，依据其访问方式判定适用性；AUTHORIZED 只取有效角色持有项，PUBLIC/AUTHENTICATED 仍须满足相应上下文。适用范围取并集，再与租户边界、资源策略上限相交。没有适用数据权限时为明确空集，不从接口许可、资源上限或缺省本人范围补足。

多项权限之间的并集与单项禁止条件组合不冲突。查询、修改、删除及其他注册操作分别计算，不跨资源或操作混合。资源策略上限不是可向用户单独授权或拒绝的入口；旧用户数据拒绝及组合策略按迁移决定处理。

### D-16：在数据访问边界落实范围

列表筛选和计数在数据库分页、排序前应用相同范围，详情、批量读取、导出、缓存命中和降级读取都应用相同约束。禁止先取全量再在前端过滤，禁止无权数据进入缓存响应或导出结果。

修改、删除及批量操作将范围加入实际写入条件，不能只做一次存在性预查。创建类操作使用注册的创建动作校验拟写入的租户、归属和部门，不能由请求者任意伪造；无法表达或未接入的动作默认拒绝。批量写入含无权记录时整体失败，事务不留下部分修改；批量读取仅返回可见记录且不泄露隐藏记录内容。

### D-17：对外失败及空范围契约

需要登录的请求缺少有效身份返回原生 401；身份有效但接口授权不成立返回 403。资源不存在或数据范围不允许访问的单条业务记录统一采用资源不可见的 404 语义，避免揭露存在性。列表范围为空返回成功的空列表与 total=0，不把空范围当全量；写操作未匹配可访问目标不得返回成功。

格式或不支持字段为 400，重复标识/关联冲突/非空删除等为 409，陈旧 If-Match 为 412，缺少必需条件头为 428。权威授权存储不可用时返回依赖失败并拒绝执行，不能回退旧 ALLOW。沿用现有统一响应与应用错误契约，401/403、OAuth、CSRF 等原生安全响应不强制改造成普通业务成功响应。

### D-18：管理 API 契约

以现有企业 API 域和平台域为边界扩展，路由示例中的前缀为企业域；平台管理使用独立的平台前缀并执行平台管理权限。

| 资源 | 对外契约 |
| --- | --- |
| 权限组 | GET/POST permission-groups；PATCH/DELETE permission-groups/{groupId}，维护父节点、名称和顺序 |
| 权限 | GET/POST permissions；GET/PATCH/DELETE permissions/{permissionId}，筛选类型、组、状态、访问方式和名称；启停使用显式状态变更 |
| 接口关联 | GET/PUT permissions/{permissionId}/interfaces，完整替换受控接口 resourceId 集合 |
| 菜单关联 | GET/PUT permissions/{permissionId}/menus，完整替换 menuId 集合 |
| 数据详情 | GET/PUT permissions/{permissionId}/data-scope，资源、操作、预设和必要部门清单作为一个整体替换 |
| 角色权限 | GET/PUT roles/{roleId}/permissions，维护明确 permissionId 清单 |
| 用户角色 | 保留 users/{username}/roles 的明确绑定入口，去除用户直接拒绝字段；认证主体、成员标识与显示名不得混用 |
| 目录与预览 | 保留接口目录和菜单 manifest 读取，增加受控数据资源/操作目录；有效权限与数据范围预览只读取持久主体、角色、成员和关联 |

新资源查询提供稳定排序与分页。集合替换明确空列表表示清空；字段缺省不变、显式 null 仅在契约允许清空时接受。新旧字段不能同时传入造成歧义。完整请求/响应类型、错误分类及前端消费一并交付，不留两个独立写入入口。

### D-19：版本与条件写入

所有修改、启停、移动、关联替换和删除要求当前版本的 If-Match；创建返回版本和 ETag。数据库使用条件更新/版本约束确保并发只有一个有效写入，不能依赖 JVM synchronized。无效请求、版本冲突、幂等冲突均不修改关系、审计、事件或授权 revision。授权关系控制版本与资源扫描版本分开，扫描不能覆盖管理员的关系版本。

### D-20：持久幂等与原子提交

创建、批量替换及授权变更使用持久 Idempotency-Key 回执，作用域包含授权域、操作者、操作和目标；指纹涵盖规范化请求及条件版本。相同键同请求返回原结果，相同键不同请求为 409。幂等处理支持并发重复请求、进程重启及不同节点，不依赖内存 Map。

权限、角色、资源关联、数据详情、授权 revision、审计、outbox 和回执按一次业务变更原子提交；失败全部回滚。返回成功发生在持久提交之后，不能先发布内存状态或通知再提交数据库。

### D-21：即时生效与一致快照

每次业务判定从权威主存储确认当前域授权 revision，不用只读副本延迟或 Token claims 替代。允许以域、主体、revision 等为键缓存不可变授权投影，但缓存 ALLOW 必须先确认当前权威版本。角色、权限、关联、数据范围、成员有效性、任职、组织关系及必要资源上限变化都必须推进相关版本，不能遗漏间接影响。

在新的短事务或明确当前读边界中读取版本和所需状态，避免复用更早的 MySQL RR 快照。读取前后复核版本，发生变化则有界重读或失败关闭，不拼装不同版本的权限与数据范围。保存响应返回以后启动的新请求必须使用新版本；已经在变更提交前完成授权的在途请求不要求撤销其已执行结果。该时间边界必须在双节点测试中可重现。

### D-22：事件传播与审计

继续使用同事务 outbox、每节点消费组、幂等 receipt、重试与死信。Redis 负责加速投影失效和分发变更，不是即时权限正确性的唯一来源；延迟、丢失、重复、乱序或 Redis 重启不能延长旧权限。保存和判定记录请求关联、主体、域、资源身份、命中权限、版本和原因；不记录凭据、完整业务正文或未授权租户数据。

### D-23：管理界面及预览

在现有 Summer UI 管理结构中提供分组树、权限列表及类型/状态筛选，使用项目现有组件。编辑表单按类型展示接口选择、菜单选择或数据资源/操作/预设选择；不出现接口权限码输入、接口访问方式字段、用户拒绝或条件表达式编辑器。

角色页面支持具体权限勾选与按组展开选择，提交前显示实际权限清单。选择父目录不产生组授权。访问方式变更影响多个资源时一次校验并给出冲突资源清单，不能部分保存。预览以真实目标主体和持久关系计算，不接受 caller-supplied roleAllows、userDenies 或 organizationIds 作为授权依据。

### D-24：管理权与初始化

权限管理、角色授权、资源关联和预览本身都受统一授权与所属域约束。企业管理员不能把平台、协议或非可配置基础设施接口绑定为企业公开接口，不能通过自行填写资源定位键绕过目录可配置性校验。现有平台/企业权限边界、活动成员校验和 OAuth 委托限制继续适用。

初始化将明确的管理权限、资源关联、管理员角色及用户角色绑定持久化，不以“没有角色即管理员”或无限超级用户分支启动系统。内置初始化内容使用确定性身份和幂等种子，重启不复活被停用的成员或普通角色授权。迁移及恢复步骤必须验证管理入口可用，同时普通业务数据仍按显式权限访问。

### D-25：生命周期与删除约束

权限可启停，停用立即使其不再贡献访问资格；再次启用必须重新验证域、资源、数据描述和访问方式一致性。type 创建后不改，避免一项已授予权限被改造成另一类资源许可。业务 code 不复用于另一权限身份。

非空分组必须先移走权限和子组才能删除；仍被角色或资源关系引用的权限必须先解除引用才能删除，不级联撤销未知关系。删除只影响新模型的可管理数据，审计、旧身份映射和迁移账本继续保留。此类管理规则不构成独立发布流程。

### D-26：旧模型迁移与授权等价

迁移先盘点当前 Capability、角色及用户绑定、接口发现历史、菜单绑定、权限包、数据上限和角色/用户策略，再生成“旧身份 → 新权限/资源/角色”账本。一个旧 code 同时承担菜单与接口用途时，拆成不同类型权限，将原有效角色授予映射到需要的各项权限；接口关联按真实目录精确建立，不根据 code 字符串猜测或通配扩大。

旧 bundle 先按有效内容展开，分类可以生成对应迁移组，但不能带入动态授权语义。旧用户拒绝必须按用户的原有效结果生成或复用等价的收窄角色，再调整绑定；不能仅清空拒绝字段。相同结果可在同域内去重迁移角色，保留来源映射，不创建新用户级拒绝通道。

旧组合数据策略、用户行级拒绝、跨操作范围或特殊公开规则，只在能够证明与五种预设及现有资源上限等价时自动转换。不能表达的项目生成阻断项，保留旧快照供核对，要求在切换前形成明确且不扩权的新配置；不得退化为 TENANT_ALL、丢弃拒绝或把不支持标记当作通过。迁移过程中的对比工具可以读取旧模型，目标运行态不得继续依赖两套业务授权事实来源。

### D-27：升级、切换及恢复

新增 schema 与数据迁移分阶段执行，复用受控真实 MySQL/Redis 环境；不假设 MySQL DDL 整体可回滚。先备份、预演并生成覆盖报告，再构造新关联、比较授权矩阵，阻断项清零后按授权域受控切换。迁移脚本可重跑，身份不重复生成，审计和版本不回退。

切换期间阻止未适配旧写入继续改变旧授权；允许旧数据只读用于核对。恢复从已验证快照和迁移账本执行，明确失败阶段、影响域及恢复检查；不能在部分切换后直接启动旧节点使其继续写入。测试必须覆盖升级中断、恢复、重跑、混合版本节点隔离和管理入口恢复。

### D-28：兼容入口与调用方迁移

新 UI、资源目录及所有自有授权消费改用新契约。确需短期保留的 Capability/角色旧入口只作为新模型适配层，通过迁移账本转换身份并执行同一版本、幂等、域和授权校验；没有第二套持久化写入逻辑。

旧用户拒绝字段、组合数据表达式或无法等价的包写入必须明确拒绝，不静默忽略。旧 Token 可继续承担身份与协议委托信息，但其历史业务权限码不能成为新授权依据。兼容期结束标准是调用方盘点、契约测试和旧写入口关闭证据齐全，不承诺所有旧 JSON 写法永久兼容。

### D-29：实施顺序与交付边界

按共享存储与授权域基础、权限/分组/关联管理、统一请求判定、菜单投影、数据范围接入、UI 和迁移验收的依赖推进。接口、菜单和数据管理可分别开发，但切换前必须形成同一授权版本的一致闭环，不能将只移除注解的中间状态部署为完成。

本规格不在当前共享工作区执行实现、迁移或服务重启；后续实施必须保存源输入和既有工作区边界，避免覆盖并行字典工作。协议例外、申请人流程和自己的会话等现有特殊入口需要逐项分类与行为回归，不得按宽泛路径一概公开或一概禁用。

### D-30：证据与完成定义

使用稳定 US/D/T/AC 编号进行双向追踪。功能交付须提供冻结源码与 schema 版本、真实测试结果、浏览器证据、升级前后矩阵及迁移阻断项报告。只记录实际执行的 tests/failures/errors/skipped，分开单测、Servlet 集成、真实 TCP、原生浏览器、双节点和迁移批次；不能将文档检查、零测试、Mock 成功或旧批次结果当作新功能验收。

## Out of Scope

- 字段可见性、字段脱敏、字段编辑权限，以及新的任意条件表达式、SQL/脚本配置和 ABAC 设计器。
- 用户直接授权、用户级显式拒绝、权限组直接授权、分组授权继承或动态权限包授权。
- 权限草稿和发布流程；本方案保存即对后续请求生效。
- 新建独立 IAM 服务、替换 OAuth/OIDC 或身份系统、重建组织体系、跨租户权限合并。
- 依靠前端定时轮询保证安全生效，或追溯取消变更提交前已完成授权的在途业务结果。
- 无证据地自动放宽无法转换的旧策略；未注册业务资源的通用 SQL 拦截式“自动保护所有表”。
- 当前规格编制阶段的业务代码实施、数据库迁移执行、服务重启、提交推送或自动拆票派工。
