# Summer 4 异常统一技术规格与 CMMI 过程执行方案

版本：1.0｜编制日期：2026-11-03（Asia/Shanghai）｜状态：可进入实施，尚未实施或验收。

本规格由已确认的 ADR 0035 决策综合形成。[GitHub Issue #173](https://github.com/abluepoint/summer/issues/173) 为需求与验收状态的权威来源；本文件是发布基线副本。后续变更同时保留版本、变更原因和追踪关系，不将编辑 Issue 正文视为既有验收自动有效。

## Problem Statement

Summer 4 维护者和 Summer Sample 开发者需要统一表达失败原因，而当前实现混用通用异常、按功能建立的专用异常和 Controller 内手工生成的错误响应。增加一个错误场景往往需要新增异常类及捕获分支，错误码、消息、HTTP 状态和字段校验明细容易失去一致性。

本次定点核查发现：SummerException 已承载 ErrorCode、消息参数、cause 和 violations，但没有独立的自定义消息入口；FieldValidationException 直接继承 RuntimeException，并重复定义字段明细类型；菜单 Controller 按异常类型手工输出包括 412 在内的状态；请求体超限通过自定义 IOException 子类在 Filter 中返回 413。现有公共 ErrorCategory 的默认映射未覆盖这些全部状态，已有 Release HTTP 测试还验证应用可将错误状态覆盖为 422。因此，仅修改继承关系不能完成本次需求。

从使用者角度，改造应消除重复定义和响应分支，让错误信息可靠到达客户端，同时维持失败条件、HTTP 状态、错误码、请求关联和协议行为。交付还需要留下可核验的需求、设计、实现、测试、评审和变更记录，便于质量管理与 CMMI 过程执行检查。

## Solution

以 SummerException 作为自有框架与业务异常的统一实现，业务差异由 ErrorCode、消息及有限的固定信息表达。仅字段校验场景保留专用子类，并继承 SummerException；不再为冲突、资源不存在、前置条件失败等场景另建自有异常类。JDK、Spring 和第三方异常保留原体系。

保留 ErrorCode、messageArguments、cause 和 violations；支持显式自定义 message，不增加通用 data/details/context 容器。API 消息优先级为：自定义 message → 国际化错误码文案 → 错误码默认文案。

应用 JSON 端点由 ApiExceptionHandler 统一生成 Unified response。只用于拼装错误响应的 Controller catch 被移除；恢复、重试、补偿以及原生协议所需的处理继续保留。公共契约与传输适配分离，不把 HTTP 状态塞入异常基类。

按 CMMI 相关实践领域组织本项目的需求追踪、技术取舍、评审、配置与变更管理、风险、验证及度量。本文给出项目级可执行安排；组织采用的模型版本、评估范围与成熟度目标尚未提供，不能仅凭本规格判定组织满足全部 CMMI 实践或取得成熟度等级。

## User Stories

以下使用“作为（As a）—我希望（I want）—以便（so that）”结构，编号同时作为稳定故事 ID。

1. **US01**：作为框架维护者，我希望自有异常复用 SummerException，以便统一维护失败信息契约。
2. **US02**：作为业务开发者，我希望不同业务错误使用 ErrorCode 区分，以便新增失败场景时无需新增异常类。
3. **US03**：作为参数契约维护者，我希望字段校验保留专用子类并继承 SummerException，以便兼顾字段语义和统一处理。
4. **US04**：作为前端开发者，我希望收到字段与校验消息组成的 violations，以便定位和展示具体输入问题。
5. **US05**：作为框架使用者，我希望异常不携带任意数据容器，以便保持公共接口边界清晰。
6. **US06**：作为业务开发者，我希望显式指定本次失败的 message，以便给出比默认文案更准确的提示。
7. **US07**：作为国际化使用者，我希望没有自定义消息时按当前请求语言解析错误码文案，以便继续获得本地化提示。
8. **US08**：作为客户端使用者，我希望消息目录缺少条目时有默认文案，以便仍可理解失败原因。
9. **US09**：作为已有调用方，我希望原消息参数保持原来的格式化含义，以便重新编译后行为不会静默改变。
10. **US10**：作为维护人员，我希望 cause 被完整保留，以便追查失败源头。
11. **US11**：作为公共接口使用者，我希望消息参数和字段明细具有稳定的集合快照语义，以便调用方修改输入集合不会改变已创建异常。
12. **US12**：作为 API 开发者，我希望由全局处理器生成应用错误响应，以便删除重复的状态和 JSON 拼装分支。
13. **US13**：作为已有 API 客户端，我希望状态码、错误码和响应结构维持原语义，以便无需跟随内部异常类型重构修改调用逻辑。
14. **US14**：作为采用条件更新的客户端，我希望前置条件失败仍返回原来的 412，以便正确区分并发冲突。
15. **US15**：作为上传或 JSON 请求的客户端，我希望请求体超限仍得到 413 和既有错误码，以便按原规则调整请求大小。
16. **US16**：作为应用集成者，我希望自定义 ErrorStatusResolver 继续生效，以便保留应用对 422 等状态的显式选择。
17. **US17**：作为安全能力维护者，我希望认证、授权和 CSRF 处理保持原协议语义，以便异常统一不改变安全链路。
18. **US18**：作为 OAuth2/OIDC 客户端，我希望协议错误不被包装为业务 Unified response，以便继续遵循标准协议交互。
19. **US19**：作为资源、SSE 和 WebSocket 使用者，我希望响应提交后的失败按原传输规则处理，以便不会收到无效的二次 JSON 响应。
20. **US20**：作为运维人员，我希望 requestId 在响应头、响应体和诊断记录中保持关联，以便定位一次失败请求。
21. **US21**：作为任务或事务维护者，我希望恢复、重试、补偿和回滚判定不依赖被删除的自有异常类，以便改造不改变执行结果。
22. **US22**：作为第三方库集成者，我希望原生异常类型继续可用，以便既有库契约和必要的 catch 语义不被破坏。
23. **US23**：作为测试人员，我希望在真实装配的 HTTP 边界验证错误行为，以便发现 advice 顺序、配置覆盖和 Filter 路径问题。
24. **US24**：作为测试人员，我希望仅为 HTTP 不可见的 cause 和构造兼容性补充契约测试，以便控制测试维护成本。
25. **US25**：作为迁移执行者，我希望每个旧异常和处理分支都有目标映射及证据，以便不遗漏嵌套、包可见或非 Exception 后缀的异常类型。
26. **US26**：作为评审者，我希望架构规则能阻止非字段校验专用异常重新引入，以便保持长期一致性。
27. **US27**：作为发布负责人，我希望公共 Java API 的兼容影响和完整制品回退方式明确，以便控制升级风险。
28. **US28**：作为需求负责人，我希望每条需求能够双向追踪到设计、测试和验收，以便明确每个变更的完成依据。
29. **US29**：作为质量负责人，我希望评审缺陷、执行结果与豁免分别记录，以便验证结论有客观证据。
30. **US30**：作为项目负责人，我希望每个阶段都有主责、依赖和出口条件，以便跟踪进度及处理阻塞。
31. **US31**：作为配置管理员，我希望需求、代码、环境和测试批次绑定到明确版本，以便复现交付结果。
32. **US32**：作为过程改进负责人，我希望记录风险、度量、变更与根因行动，以便持续改进异常治理过程。

## Implementation Decisions

### D01 — 异常类型与模块边界

Summer Common 负责稳定的错误与消息契约；Summer MVC 负责字段校验和 HTTP 适配；Summer Security 及其装配层保留安全扩展与协议处理；Summer Sample 迁移业务抛出点和重复响应分支。Summer Data JPA 等其他模块如发现自有非字段异常，也纳入同一规则，不扩大为业务规则或 SQL 行为重构。

仅字段校验专用子类获得保留资格。类型名称含 Validation 不自动等于字段校验：必须实际表达字段级约束并使用固定 violations。其余领域校验、资源状态、幂等、版本冲突、执行失败统一用 SummerException 与具体 ErrorCode 表达。禁止仅将旧类改为继承 SummerException 后全部保留，也禁止用匿名自有异常子类规避规则。

此规则约束自有异常类的定义及原自有异常迁移，不强制包装所有 JDK、Spring 或第三方抛出的异常，也不把 Java 编程错误无差别转换为业务失败。

### D02 — 信息模型与创建契约

ErrorCode 必须存在，消息参数继续作为模板参数，violations 为固定字段/消息列表，cause 保留原异常链。沿用现有数组和列表的防御性复制；不承诺对参数中任意对象深复制，不将参数槽用作隐蔽的业务数据容器。

现有 SummerException 的公开构造签名及原参数语义保持。新增自定义消息采用明确命名的创建入口，例如 withMessage；不增加会抢占既有字符串 varargs 调用的新构造重载。内部构造路径统一初始化公共字段，允许 message 与 cause 同时存在，并使字段校验子类复用同一信息实现。最终公开入口保持最小集合，不另建可变 builder 或通用上下文对象。

以 null 表示没有显式 message；非 null 消息按调用方提供的字符串原样使用，包括空字符串、空白和占位符字符，不做隐式 trim 或再次模板插值。未显式提供 message 的调用仍沿用既有模板参数解析。该规则使“原样优先”可精确验证，也避免从 getMessage 是否非空猜测消息来源。

getMessage 在存在显式消息时返回该消息，否则返回错误码默认文案；请求语言下的解析留在消息适配流程中，不依赖线程中偶然存在的 HTTP 上下文。cause、堆栈和内部诊断对象不新增为 API 响应字段；未知技术异常继续使用既有内部错误兜底。显式 API 消息由业务调用方负责提供，不自动取第三方异常正文作为公开消息。

### D03 — 字段校验与消息解析

FieldValidationException 改为继承 SummerException，复用统一字段明细和错误码；不再维护第二套相同含义的信息存储。既有字段明细类型存在调用引用时，在迁移批次中同步调整调用方；公开类型签名变化须列入 Java API 兼容清单，不能冒称二进制兼容。

参数契约与 Bean Validation 的输入范围及校验语义保持。自有字段异常走统一 SummerException 响应路径；Spring 原生校验异常由已有适配入口转换为同一响应结构，无需修改其继承关系。多个字段、嵌套字段、空明细的结构和既有顺序保持。

API 提示执行已确认优先级：显式 message 原样输出；否则按请求 Locale 用错误码及 messageArguments 解析；找不到国际化条目时使用 defaultMessage。保留框架错误与业务错误各自命名空间，不通过提示文本判断错误类型。

### D04 — HTTP 状态与业务错误码

迁移前建立“触发条件—旧异常—旧错误码—HTTP 状态—消息来源—响应头—处理入口—新 ErrorCode”的完整映射表，并以固定源码和特征测试锁定。标准类别继续委派现有默认解析器；412、413 等不能由现有类别表达的状态，通过适配层明确注册的具体 ErrorCode 映射保留。应用提供的 ErrorStatusResolver 继续具有原有覆盖能力，422 覆盖回归必须通过。

本次不为保留状态而向异常类添加 HTTP 字段，也不依赖错误码前缀、后缀或 message 字符串猜状态。新框架码与新业务码继续遵循 ADR 0009；既有业务错误占用框架前缀的历史问题单独登记，不在本次兼容性迁移中偷偷改码。需要改码时走独立变更记录并重新评估客户端影响。

### D05 — 统一响应入口及前置边界

删除应用 JSON Controller 中仅将异常转为 ResponseEntity/ApiError 的重复 catch，将状态、消息、violations、requestId 的输出归 ApiExceptionHandler。应用自定义解析器、安全方法处理器与全局兜底的优先级通过真实装配测试验证，不单靠直接调用 handler 的单测。

Filter 中发生的自有应用错误不会自动进入 ControllerAdvice。请求体超限改为统一异常后，在该前置边界通过现有 MVC 异常解析机制显式委派统一出口，并验证返回 413、原错误码和 requestId；未解析成功时保持受控失败，不能继续执行正常业务或返回成功响应。原生 IOException 的传播仍遵循 Servlet 契约，不新建自有 IOException 子类。

认证入口、访问拒绝和协议端点继续使用对应的原生扩展点；能复用的公共响应契约保持一致，不以业务全局 handler 接管 OAuth2/OIDC。Raw response、Actuator、文件、Range、SSE 和 WebSocket 沿用既有边界；响应已提交时不再次写业务 JSON。请求头、内容类型与成功响应行为均按迁移映射保持。

### D06 — 局部控制流程与非 HTTP 消费者

保留真正的重试、补偿、事务回滚、降级和资源清理逻辑。旧逻辑按自有异常类型判断时，改为稳定 ErrorCode 或其业务类别判断，不按消息文本判断，不扩大为捕获所有 RuntimeException 后统一吞掉。同步核查事务 rollback/noRollback 配置、重试/熔断异常选择器、监听器、调度任务和 WebSocket 关闭码。

只迁移表达方式，保持次数、退避、幂等语义、失败分类和最终业务状态。必要的第三方类型判断继续保留。

### D07 — 迁移与兼容策略

执行顺序为：固定基线与特征测试 → Common 创建契约 → MVC 字段/消息/状态路径 → 前置过滤与安全回归 → Sample 各业务簇及非 HTTP 消费者 → 删除失去引用的旧异常 → 全量受影响门禁。

每批必须闭合“定义、抛出点、catch/instanceof、配置引用、测试夹具、对外映射”；迁移清单完成前不得只根据编译通过宣布完成。最终生产代码不保留违反 D01 的临时兼容异常类。公开类的删除或类型签名变化按实际影响列入发布说明，并按仓库版本政策处理；现有构造语义兼容与已删除类的二进制兼容分开报告。

不改数据库结构、存量业务数据、接口路由或 ApiResponse/ApiError 信封字段。回退以整套已验证代码/制品版本为单位，不混用新 Common 与旧调用模块。若公共工作区包含其他任务改动，先固定实际实施基线与差异来源，不覆盖、清理或提交不属于本任务的内容。

## Testing Decisions

### 已确认的测试边界

用户于 2026-11-03 确认：以现有 Spring Boot + MockMvc 的应用 HTTP 边界为主；对 HTTP 无法观察的 cause 与构造兼容性补少量 Common 契约测试；复用协议和真实 HTTP 回归。不为本功能增加测试专用生产接口，不将每个内部方法拆成独立 mock 测试缝隙。

优先复用 ApiExceptionHandlerTest、DefaultErrorStatusResolverTest、ReleaseErrorStatusHttpTest、MethodSecurityExceptionHandlerTest，以及已有请求体缓存、字段校验、任务恢复和实时消息测试。ReleaseErrorStatusHttpTest 已展示完整装配及应用覆盖状态的验证方式。直接调用 handler 的测试只能作为局部证据，不能替代过滤器、安全链与 advice 的组合验证。

好的测试从合法调用入口制造具体失败，检查可观察的状态、错误码、消息、字段明细、请求关联和业务结果；不锁定私有方法、内部对象分配次数或实现调用顺序。异常白名单检查属于显式架构要求 R01 的验证，与功能行为测试分别报告。

| T01 类型与基线 | 枚举生产模块全部异常继承链、嵌套/包可见类型及调用、配置引用 | 每项有迁移决定；最终仅允许基类与字段校验子类；第三方类型不被误计为自有定义 |
| T02 Common 契约 | 原三类构造调用、字符串/数组模板参数、新消息入口、message+cause、复制后修改输入 | 原重载含义不变；cause 身份/链保持；参数和列表结构快照不变；没有通用上下文属性 |
| T03 消息优先级 | 显式消息配有/无翻译；null、空串、空白、占位符字符；至少两种 Locale；翻译缺失 | 显式非 null 消息原样输出；null 走模板；缺条目用默认；请求间语言不串扰 |
| T04 校验 | 参数契约和 Bean Validation 的单字段、多字段、嵌套字段及空明细 | 原输入约束、字段路径、消息、顺序及错误结构保持；统一异常继承路径生效 |
| T05 全局响应 | 完整装配的普通业务失败、未知技术失败、已有请求 ID、未提供请求 ID | 错误信封只输出一次；状态/类型正确；requestId 一致；未知失败使用内部错误兜底，不增加 cause/堆栈字段 |
| T06 状态兼容 | 映射清单中所有不同错误码/状态/入口组合，含 400/401/403/404/409/412/413 和既有其他状态 | 与固定基线一致；检查响应头；应用 422 覆盖仍有效，不靠码字符串推断 |
| T07 Filter 超限 | 实际启用 Filter 的允许大小、边界大小、超限和原生 I/O 失败 | 正常请求仍成功；超限在进入业务前返回原 413 合约；不吞真实 I/O 错误，不发生双写 |
| T08 安全与协议 | 匿名、无权限、方法安全、CSRF、OAuth2/OIDC 正常与错误请求 | 原安全结果和协议格式保持；业务包装不侵入协议；应用 JSON 的既有错误结构保持 |
| T09 资源与长连接 | Raw response、Actuator、文件/Range、SSE 和 WebSocket，含响应提交后的失败 | 保持原状态/头/关闭码/事件契约；不追加第二个 JSON 信封 |
| T10 行为恢复 | 代表性的可重试与不可重试错误、幂等冲突、前置条件、补偿/回滚 | 重试次数和最终状态与基线一致；业务拒绝不误升级为技术重试；第三方 catch 行为保持 |
| T11 集成与回退 | 受影响模块编译/打包、公共调用方编译夹具、同版制品组合及回退演练 | 无缺失类型/链接错误；兼容差异有清单；回退后核心错误契约与健康检查通过 |
| T12 迁移闭合 | 对比迁移清单、生产类型、Controller 分支、配置、测试及实际运行证据 | 无未处理旧异常引用，无仅拼响应的重复分支；合理保留项均有依据 |

真实 HTTP 补验复用既有入口，至少覆盖普通 JSON 错误、Filter 413、方法安全拒绝、协议错误和一个实际受影响的长连接边界。需要 MySQL/Redis 的已有测试使用受控测试环境并记录版本和资源归属；MockMvc、内存数据库或受控替身不能被标注为真实 TCP 或生产依赖验收。未新增浏览器全量验收要求；若发现实际前端契约变化，再通过变更记录增加相关浏览器验收。

## Out of Scope

- 新增通用异常上下文、任意 payload、可变异常数据袋或每个业务场景一套异常子类。
- 重写 JDK、Spring 和第三方异常继承体系，或无差别包装所有技术异常。
- 新增数据库迁移、业务表、接口路由、权限模型或前端错误组件体系。
- 改变 OAuth2/OIDC、资源与长连接的原生响应规则，或将 HTTP 元数据放入 Common 异常。
- 顺带改造所有旧业务错误码命名、全部包结构或产品模块归属；已识别问题另建变更。
- 本轮直接修改生产代码、部署、创建测试数据或声称测试已经通过。
- 组织级 CMMI 评估、特定成熟度评级、高成熟度统计过程能力证明或购买模型/培训服务。
